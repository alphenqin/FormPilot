# 一、产品概述

## 1.1 产品背景

随着企业招聘线上化，求职者需要在不同招聘网站、企业招聘官网和校园招聘系统中重复填写个人信息。

不同平台的表单结构、字段名称和填写规则存在差异，传统自动填表工具主要依赖关键词匹配和固定规则，难以处理复杂的业务场景。

目前主要存在以下问题：

1. 重复填写：不同招聘平台需要反复填写相同的个人信息。
2. 字段理解不准确：同一个字段在不同平台可能使用不同名称，简单关键词匹配容易出错。
3. 信息缺失：简历中没有明确的信息无法自动补充，用户需要自行发现并填写。
4. 信息冲突：简历、历史填写记录和网页已有内容可能不一致。
5. 经历错配：多段教育、工作、实习和项目经历容易出现字段交叉匹配。
6. 复杂控件难处理：自定义下拉框、级联选择、动态经历等控件难以统一适配。
7. 填写结果不可靠：部分网页即使执行了赋值操作，也可能没有真正保存。
8. 隐私安全：简历包含大量个人敏感信息，用户对云端存储和数据使用存在顾虑。

FormPilot 希望通过大模型、规则引擎和浏览器自动化技术，将求职者的个人资料转化为可追溯的结构化事实资产，实现智能识别、智能决策、自动填写和结果核验。

## 1.2 产品定位

FormPilot 是一款面向求职者的 AI 智能求职助手。

用户只需建立一次个人经历档案，系统便可以在用户访问企业招聘网站时，自动识别网页表单，结合个人资料理解字段含义，生成填写计划，并在用户授权后完成填写。

它不仅是一个自动填表工具，更是一个围绕个人经历资产构建的智能求职 Agent。

核心能力包括：

- 个人经历结构化管理。
- AI 简历解析。
- 网页表单智能识别。
- JD 岗位需求分析。
- 个人经历与岗位要求匹配。
- 缺失信息主动追问。
- 冲突信息智能识别。
- 网页表单自动填写。
- 实际填写结果核验。
- 求职资料多版本管理。

## 1.3 产品核心理念

**让 AI 理解用户的真实经历，而不是简单地复制简历。**

系统需要明确区分：已有事实、待确认事实、用户临时补充的信息、模型推断的信息、网页已有的信息、最终经过用户批准的填写内容。

AI 负责理解和决策，规则引擎负责约束，浏览器负责执行，用户保留最终控制权。

# 二、产品目标与版本规划

## 2.1 MVP 核心目标

**用户上传一份简历，即可在一个经过适配的企业招聘网站上完成可靠的智能网申填写。**

完整业务流程：

1. 用户注册或进入本地工作空间。
2. 上传个人简历。
3. AI 解析简历。
4. 建立个人经历资产库。
5. 用户确认关键事实。
6. 用户访问企业招聘网站。
7. 浏览器扩展识别网页表单。
8. AI 分析表单字段。
9. 匹配个人经历事实。
10. 自动发现缺失信息。
11. 主动向用户提问。
12. 识别已有信息冲突。
13. 生成填写计划。
14. 用户确认填写内容。
15. 浏览器执行自动填写。
16. 回读网页实际值。
17. 生成填写结果报告。
18. 用户自行检查并提交申请。

MVP 不追求网站数量，而是优先保证完整业务闭环。

## 2.2 产品版本规划

| 版本 | 核心功能 | 目标 |
|---|---|---|
| V1.0 | 简历解析、事实资产库、AI 表单识别、智能填写、回读核验 | 跑通网申闭环 |
| V1.1 | 复杂控件、动态经历、多网站适配 | 提高兼容性 |
| V1.2 | JD 解析、岗位匹配、经历证据匹配 | 智能求职 |
| V1.3 | 简历多版本、开放题生成、岗位定制 | 提高求职质量 |
| V2.0 | 岗位推荐、投递记录、求职 Agent | 完整求职平台 |

当前只开发 V1.0，其他版本预留合理的扩展能力。

# 三、产品整体架构

## 3.1 架构设计

FormPilot 采用独立的模块化架构，整体划分为五个核心层。

| 层次 | 责任 | 主要模块 |
|---|---|---|
| 用户交互层 | 用户与产品的交互 | 浏览器扩展、插件弹窗、个人资料管理、简历管理、填写计划预览、执行结果展示 |
| 浏览器执行层 | 网页识别和自动化操作 | 网页扫描器、DOM 解析器、表单字段识别器、控件适配器、填写执行器、回读核验器、撤销管理器、站点适配管理器 |
| AI 智能决策层 | 理解自然语言、个人经历和网页表单 | 简历解析、事实抽取、JD 解析、字段语义匹配、经历实体匹配、缺项检测、冲突检测、填写计划生成 |
| 业务服务层 | 统一管理产品业务 | 用户、个人资料、简历、求职任务、AI 模型、任务状态、权限、数据同步服务 |
| 数据存储层 | 管理个人资料、任务和系统数据 | 用户信息、个人事实、个人经历、原始简历、事实证据、表单快照、填写计划、用户补充答案、执行记录、个人偏好 |

## 3.2 技术架构原则

1. 前后端职责分离。
2. 浏览器扩展与算法服务解耦。
3. AI 模型调用统一封装。
4. 业务规则独立于 Prompt。
5. 结构化数据优先于非结构化文本。
6. 所有重要操作支持追溯。
7. 核心业务接口保持版本化。
8. 本地优先存储个人资料。
9. 复杂网页操作采用适配器模式。
10. 所有关键执行过程必须可核验。

具体技术选型由开发阶段结合实际需求确定，不得为了使用某种技术而引入不必要的复杂度。

# 四、核心业务模块

## 4.1 个人经历资产库

将用户简历转换为结构化、可管理、可追溯的个人经历资产，这是整个产品的基础。

| 分类 | 字段示例 |
|---|---|
| 基本信息 | 姓名、性别、电话、邮箱、现居城市 |
| 教育经历 | 学校、专业、学历、入学时间、毕业时间 |
| 工作经历 | 公司、职位、部门、任职时间、工作内容 |
| 实习经历 | 公司、岗位、实习时间、实习内容 |
| 项目经历 | 项目名称、角色、项目时间、项目描述 |
| 专业技能 | 技术栈、技能等级、熟练程度 |
| 证书信息 | 证书名称、获取时间、证书编号 |
| 求职意向 | 目标城市、行业、岗位、薪资范围 |

解析流程：上传简历 → 文本提取 → 文档分块 → AI 结构化抽取 → 事实标准化 → 规则校验 → 证据关联 → 用户确认 → 保存个人经历资产。

Fact 数据模型，每个事实必须具有唯一标识：

```json
{
  "fact_id": "fact_work_001",
  "category": "work",
  "path": "work.company",
  "value": "星河科技",
  "entity_id": "work_001",
  "confirmation": "confirmed",
  "source_type": "resume",
  "evidence_ids": ["evidence_001"]
}
```

Evidence 数据模型：

```json
{
  "evidence_id": "evidence_001",
  "document_id": "resume_001",
  "page": 1,
  "block_id": "block_004",
  "quote": "曾在星河科技担任后端开发实习生"
}
```

关键要求：

- 每个事实拥有独立 ID，并关联来源。
- 支持同一事实的多个证据。
- 支持事实冲突识别、用户修改、历史版本。
- 未确认事实不得直接进入自动填写执行。
- 工作、教育、项目等经历必须独立绑定实体。
- 临时补充的信息与长期个人档案分开管理。

## 4.2 简历智能解析

支持 PDF、TXT、用户手动输入；首版不强制支持扫描件 OCR。

解析要求：

1. 识别简历章节。
2. 提取个人基本信息。
3. 提取教育经历。
4. 提取工作经历。
5. 提取实习经历。
6. 提取项目经历。
7. 提取专业技能。
8. 提取证书。
9. 识别时间范围。
10. 识别事实之间的关系。
11. 关联原文证据。
12. 输出标准化 JSON。

不得让模型直接生成未经核实的个人事实。对于缺少明确依据的信息，必须标记为待确认。

## 4.3 网页表单智能识别

自动识别当前招聘网站中的表单结构。

```json
{
  "field_id": "f001",
  "label": "最高学历",
  "control_type": "select",
  "required": true,
  "current_value": "",
  "options": ["本科", "硕士", "博士"],
  "constraints": {},
  "visible": true,
  "enabled": true
}
```

V1.0 支持 text、textarea、email、phone、date、month、select、radio、checkbox、file。

V1.1 支持自定义下拉、级联选择、日期选择器、动态经历组件、多段经历、Shadow DOM。

扫描规则：

- 识别 label、name、id、placeholder、ARIA。
- 获取当前值、必填状态、字段约束、选项集合、字段之间的分组关系。
- 过滤无关隐藏字段。
- 为当前表单生成快照。
- 支持页面动态变化后的重新扫描。
- 不得将整个网页无差别发送给 AI 模型。

## 4.4 AI 智能字段匹配

系统需要理解字段真实含义，而不是依赖简单的字段名称匹配。例如简历中“现居城市：杭州”不能因为包含“城市”就直接匹配网页的“期望工作城市”。

| 类型 | 含义 | 处理 |
|---|---|---|
| fill | 有可靠事实 | 生成待批准填写项 |
| ask | 缺少信息 | 主动询问 |
| review | 存在冲突或歧义 | 等待确认 |
| manual | 需要人工处理 | 展示人工入口 |
| skip | 无需处理 | 跳过 |

核心规则：

- 事实匹配：只有语义和业务含义一致，才能直接匹配。
- 信息完整性：不允许根据常识补造个人事实。
- 信息冲突：网页已有值与简历不同，保留网页值并要求用户确认。
- 经历绑定：同一经历的公司、岗位、时间和工作内容必须绑定同一个 entity_id。
- 日期精度：不能将年月信息自动补成具体日期。
- 时间关系：合理的项目和实习时间重叠不能直接判断为错误。
- 信息作用范围：用户本次补充的信息默认只作用于当前任务。

## 4.5 主动追问系统

系统根据网页字段和个人资料自动生成待补充问题，例如意向城市、可到岗时间、期望薪资、是否接受调剂。

问题需要关联 question_id、field_id、问题内容、答案类型、是否必填、当前答案、答案来源、信息作用范围。

支持文本回答、单选、多选、日期选择、数字输入。相同事实尽量只追问一次，用户回答后重新生成填写计划。

## 4.6 填写计划管理

执行前必须生成填写计划，包括网页字段、当前值、目标值、来源事实、证据引用、决策类型、决策原因、是否需要用户确认。

用户可以修改填写值、取消填写、保留网页已有值、确认替换、查看原始证据。

**未经用户批准的填写计划不得执行。**

## 4.7 浏览器自动执行

将经过用户批准的填写计划准确写入网页。

执行流程：用户批准 → 检查表单快照 → 检查字段原值 → 定位目标控件 → 执行填写 → 触发必要事件 → 回读实际值 → 验证网站校验状态 → 生成执行报告。

执行原则：

- 逐字段执行、逐字段记录。
- 单字段失败不影响其他独立字段。
- 动态组件重新定位。
- 受控组件采用正确事件机制。
- 页面发生变化时暂停过期计划。
- 不自动提交申请。
- 不绕过验证码或网站权限。

## 4.8 填写结果核验

不能以赋值成功作为填写成功的判断标准，必须重新读取网页实际值。

| 状态 | 含义 |
|---|---|
| verified | 实际值一致且校验通过 |
| failed | 写入失败 |
| manual | 需要人工处理 |
| skipped | 未执行 |

必须区分定位失败、控件不支持、值未持久化、网站校验错误、页面结构变化、用户中途修改。

撤销只恢复本次操作成功写入且之后未被用户修改的字段，不能覆盖用户后来修改的新值；不保证撤销第三方网站已经自动保存的数据。

# 五、求职智能化扩展模块

以下功能作为后续版本规划，不影响 V1.0 的核心开发。

## 5.1 JD 岗位解析

用户打开招聘详情页面，系统自动提取岗位名称、公司名称、工作地点、学历要求、专业要求、工作年限、技能要求、岗位职责、优先条件、其他限制。

区分硬性条件、核心能力和优先条件，每个条件必须关联 JD 原文。

## 5.2 个人经历反向匹配

将岗位要求与个人经历资产库进行匹配。

| 状态 | 含义 |
|---|---|
| 已匹配 | 存在明确事实证据 |
| 证据不足 | 可能具备，但资料不足 |
| 待确认 | 需要用户补充 |
| 不匹配 | 明确不满足条件 |

不能仅根据关键词相似度生成最终结论。

## 5.3 简历岗位定制

根据 JD 和个人经历生成岗位版本简历。要求保留原始简历，只使用真实经历，不编造工作业绩、不虚构项目数据，记录修改内容，保留不同岗位版本，支持用户审核和导出。

## 5.4 开放题智能生成

对于“请介绍你的优势”“为什么选择我们公司”“描述一次项目经历”“你最大的挑战是什么”等开放题，系统结合岗位要求和个人经历生成答案建议。

所有生成内容必须基于已确认事实，用户修改后才能使用。

# 六、系统接口设计

V1.0 先定义以下四个核心算法接口。

## 6.1 简历解析

`POST /v1/profile/parse`

- 输入：document_id、document_revision、source_blocks。
- 输出：事实候选、证据、解析异常、确认状态。

## 6.2 生成填写计划

`POST /v1/fill/plan`

- 输入：task_id、profile_revision、form_snapshot、confirmed_facts、task_answers。
- 输出：plan_id、plan_revision、form_snapshot_id、dom_fingerprint、field_decisions、questions、entity_bindings、status、degraded。

## 6.3 重新生成填写计划

`POST /v1/fill/resolve`

- 输入：plan_id、expected_plan_revision、answers、client_request_id。
- 输出：新版本计划、更新后的字段决策、剩余问题、当前任务状态。

## 6.4 执行结果核验

`POST /v1/fill/verify`

- 输入：task_id、plan_id、plan_revision、form_snapshot_id、user_approval、execution_report。
- 输出：verified_fields、failed_fields、remaining_manual_fields、status、application_submitted。

四个接口统一请求响应格式、异常码、版本控制和幂等机制。具体 Schema 在 M3 阶段确定，并配套 JSON Schema 和自动化测试。

# 七、任务状态机

```text
DRAFT → PLANNED → WAITING_USER → READY → WRITING → REVIEW
```

| 状态 | 说明 |
|---|---|
| DRAFT | 任务初始化 |
| PLANNED | 已生成填写计划 |
| WAITING_USER | 等待补充或确认 |
| READY | 用户批准 |
| WRITING | 执行填写 |
| REVIEW | 等待结果核对 |

重要约束：

1. 补充答案后生成新版本计划。
2. 用户修改个人资料后重新检查。
3. 页面结构变化后重新扫描。
4. 旧计划不得执行。
5. 失败字段必须明确展示。
6. 人工项未完成不能显示全部完成。
7. 不允许将网页填写完成等同于申请提交成功。

# 八、数据存储与安全

## 8.1 数据存储

个人资料优先本地存储。

- IndexedDB：浏览器端个人资料及任务缓存。
- SQLite 或 PostgreSQL：服务端结构化业务数据，按实际部署需求确定。
- 对象存储：用户授权后的文件存储。
- Redis：仅在确有任务缓存或分布式协调需求时引入。

不要求首版引入所有基础设施。

## 8.2 隐私原则

1. 本地优先。
2. 最小必要上传。
3. 数据传输加密。
4. 个人资料加密存储。
5. 用户明确授权模型处理。
6. 不在日志中记录简历正文。
7. 不在插件中保存服务端密钥。
8. 支持查看、修改、删除。
9. 不默认共享用户资料。
10. 网页内容和简历内容均视为不可信输入。

# 九、非功能性需求

| 维度 | 要求 |
|---|---|
| 可维护性 | 模块边界清晰，核心逻辑可独立测试 |
| 可扩展性 | 新增招聘网站不应修改核心填写引擎 |
| 稳定性 | 单字段异常不导致整个任务丢失 |
| 安全性 | 用户授权、数据隔离、最小权限 |
| 可追溯性 | 事实、计划、执行结果均可追溯 |
| 兼容性 | 优先支持主流 Chromium 浏览器 |
| 性能 | 简历解析及计划生成有明确超时和降级策略 |
| 可测试性 | 算法、规则、插件和适配器均有测试 |
| 可恢复性 | 支持任务恢复、重新扫描及安全重试 |

# 十、项目开发阶段

## M0：项目初始化与基础架构

目标：建立独立、完整的 FormPilot 项目工程。

任务：初始化项目仓库、确定技术栈、设计整体架构、建立前端工程、浏览器扩展工程、后端服务工程、算法服务接口、统一数据模型、开发环境及配置管理、基础测试框架、项目开发文档。

验收：项目可以独立运行，前后端及插件能够完成基础通信。

## M1：个人经历资产库

目标：完成简历到结构化个人事实的转换。

任务：简历上传、PDF 文本提取、AI 事实抽取、证据关联、事实确认、个人资料管理、数据版本控制。

验收：能够解析一份真实简历并建立完整的结构化档案。

## M2：网页表单识别

目标：完成浏览器表单扫描和字段结构化。

任务：网页识别、DOM 扫描、字段识别、控件类型识别、表单快照、字段定位、动态页面重新扫描。

验收：能够识别目标测试网站的主要表单字段。

## M3：AI 智能决策

目标：实现个人事实与网页字段的智能匹配。

任务：事实匹配、经历实体绑定、字段决策、缺项识别、冲突识别、主动追问、用户答案处理、填写计划生成。

验收：能够正确处理 fill、ask、review、manual、skip 五种决策。

## M4：自动填写闭环

目标：完成真正可用的自动填写功能。

任务：用户确认计划、浏览器自动填写、控件适配、回读核验、错误处理、单字段重试、撤销机制、任务恢复、12 个边界用例测试。

验收：能够在一个真实授权的招聘网站完成整个填写闭环。

## M5：智能求职扩展

目标：将 FormPilot 从智能填表工具升级为求职 Agent。

任务：JD 解析、岗位匹配、证据匹配、简历定制、开放题生成、多网站适配、投递记录管理。

# 十一、项目质量与测试标准

准备 10 份脱敏简历 × 3 套表单模板，共 30 个标准测试任务。

| 指标 | 目标 |
|---|---:|
| 首次填值正确率 | ≥95% |
| 正确自动覆盖率 | ≥80% |
| 关键事实错误 | 0 |
| 无依据事实写入 | 0 |
| 错误经历绑定 | 0 |
| 未经确认覆盖原值 | 0 |
| 未经授权自动提交 | 0 |

另外必须完成 12 个边界测试：

1. 现居城市不能自动当作意向城市。
2. 年月不能自动补成具体日期。
3. 网页已有信息冲突不能直接覆盖。
4. 多份简历信息冲突需要确认。
5. 多段实习经历不能交叉匹配。
6. 项目时间异常需要识别。
7. 合理时间重叠不能误判。
8. React 组件写入后清空必须识别。
9. 页面变化后不能执行过期计划。
10. 不存在的事实和字段 ID 必须拒绝。
11. 模型超时和无效输出必须安全降级。
12. 用户修改后撤销不能覆盖新值。

# 十二、Codex 开发要求

本项目采用从零开始的独立工程设计方式。将 FormPilot 作为一个完整的新产品进行开发，不依赖任何既有项目的目录结构、业务模型和代码组织方式。

## 12.1 第一阶段：技术方案设计

收到本 PRD 后，先不要立即生成大量代码。先完成：

1. 分析产品需求。
2. 设计整体系统架构。
3. 确定前端、插件、后端及算法服务技术栈。
4. 设计核心数据模型。
5. 设计 API 接口。
6. 设计浏览器扩展架构。
7. 设计 AI 算法模块。
8. 设计项目目录结构。
9. 制定 M0～M5 开发计划。
10. 输出技术选型及选择理由。

**先提交完整技术方案，等待确认。**

## 12.2 第二阶段：独立工程建设

从空白工程开始建立 FormPilot。统一项目命名、代码规范、接口规范、错误码、日志规范、数据模型、配置管理、测试规范。不要将产品逻辑全部堆积在一个文件中。

## 12.3 第三阶段：分阶段实现

严格按照 M0 → M1 → M2 → M3 → M4 的顺序实施。每个阶段必须完成功能实现、单元测试、接口测试、集成测试、文档更新、阶段验收。

未经确认，不得擅自扩大当前阶段范围。

## 12.4 代码质量要求

1. 保持架构清晰。
2. 避免重复代码。
3. 避免大量 if/else 堆砌。
4. 不为精简而精简。
5. 合理划分模块职责。
6. 避免过度设计。
7. 不使用大量 Mock 冒充真实功能。
8. 重要业务逻辑必须可测试。
9. 所有模型输出必须经过结构化校验。
10. 所有浏览器操作必须有实际结果核验。

## 12.5 每阶段交付报告

每完成一个阶段，必须输出：完成功能、项目目录变化、核心代码模块、数据模型变化、API 变化、测试结果、性能情况、未解决问题、下一阶段任务。

# 十三、最终产品验收

FormPilot V1.0 最终必须实现以下场景：

用户上传简历，系统建立个人事实资产库。用户打开企业招聘网站，插件识别当前页面的招聘表单。AI 理解网页字段，将其与个人真实经历匹配。遇到缺失信息时主动询问用户，遇到冲突信息时要求用户确认。用户可以查看每个字段的原始依据和目标填写值。

用户确认后，插件执行填写。系统逐字段读取实际网页值，判断是否成功。失败字段能够定位、重试或交由人工处理。用户可以撤销本次填写。最终申请提交操作始终由用户完成。

**FormPilot 的最终目标，是建立一个以个人真实经历为核心、以 AI 为决策引擎、以浏览器自动化为执行能力的智能求职平台。**
